# Intent MILEAGE: правило пробега в решении по заявке

Опора: интервью Grill Me — `grill_MILEAGE.md` (все вопросы закрыты заказчиком).

## 1. Замысел

Добавить в расчёт решения по заявке (approve / review / reject) проверку
пробега автомобиля: пробег не больше 400 000 км — решение считается по
текущей логике LTV без изменений; пробег больше 400 000 км — заявка, которая
по LTV получила бы approve, понижается до review. На review и reject по LTV
пробег не влияет. Меняется только расчёт решения по заявке.

## 2. Зачем

Сегодня решение по заявке зависит только от LTV, пробег на него не влияет
(код: backend/src/Domain/DecisionEngine.php). Заказчик требует учитывать
пробег при принятии решения: автомобиль с пробегом больше 400 000 км не
должен получать approve по LTV — такая заявка уходит в review (ответ в
интервью — формулировка задачи).

## 3. Constraints

1. Граница включительная: 400 000 км — ещё «не больше», решение по LTV;
   400 001 км — первое значение, на котором правило срабатывает. — ответ в
   интервью (формулировка задачи: «не больше 400 000 км, иначе review»).
2. Правило понижает только approve до review. Review-зона LTV остаётся
   review; reject не смягчается: при LTV > 85% итог — reject независимо от
   пробега. — ответ в интервью (вопрос 1).
3. Существующая логика решения по LTV не меняется: LTV < 60% → approve;
   60% <= LTV <= 85% → review; LTV > 85% → reject. — код:
   backend/src/Domain/DecisionEngine.php, числа 60 и 85 — код:
   backend/config/rules.php; неизменность подтверждена — ответ в интервью
   (вопросы 1, 5).
4. Диапазон валидации пробега 0..500 000 км не меняется; значения
   400 001..500 000 — валидный вход. — код: backend/config/rules.php;
   ответ в интервью (вопрос 5).
5. Пробег не указан (поле отсутствует или null) — заявка отклоняется
   ошибкой валидации, решение не рассчитывается. — код:
   backend/src/Domain/ApplicationValidator.php.
6. Пустая строка пробега приводится к 0 км и валидна, как и явный 0 км:
   решение по LTV. Известная дыра, сознательно не закрывается. — код:
   backend/src/Domain/ApplicationValidator.php; ответ в интервью (вопрос 2).
7. `approved_limit` при review из-за пробега — 0, как у всех не-approve
   решений. — код: backend/src/Domain/AssessmentService.php; ответ в
   интервью (вопрос 3).
8. Правило действует только на расчёт решений по новым заявкам; уже
   сохранённые решения не пересчитываются. — ответ в интервью (вопрос 4).

## 4. Open questions

Открытых вопросов нет. Вопросы интервью закрыты заказчиком (подробности —
`grill_MILEAGE.md`):

- «review или reject при пробеге > 400 000 км и одновременно плохом LTV» —
  закрыт: заказчиком (вопрос 1): reject, правило понижает только approve.
  Сверка с формулировкой задачи: «иначе — review» буквально перекрыло бы и
  reject; заказчик подтвердил, что reject сохраняется, расхождение снято
  его ответом.
- «пустая строка / 0 км как "пробег не указан"» — закрыт: заказчиком
  (вопрос 2): валидация не меняется, дыра `'' → 0` остаётся вне рамок.
- «`approved_limit` при review из-за пробега» — закрыт: заказчиком
  (вопрос 3): 0, как у всех не-approve решений.
- «пересчёт сохранённых решений» — закрыт: заказчиком (вопрос 4): правило
  только на новые заявки, пересчёт не нужен.
- «радиус задачи» — закрыт: заказчиком (вопрос 5): только расчёт решения.

## 5. Не входит

- Валидация входа заявки: диапазон пробега 0..500 000 км, поведение при
  отсутствии поля, null, пустой строке и явном нуле. — ответ в интервью
  (вопросы 2, 5).
- Пересчёт уже сохранённых решений по новому правилу. — ответ в интервью
  (вопрос 4).
- Задача LOAN-12: расчёт лимита по возрасту автомобиля. — ответ в интервью
  (вопрос 5).
- Всё, кроме расчёта решения: хранение заявок, структура и тестовые данные
  БД, HTTP-слой, фронтенд, моки. — ответ в интервью (вопрос 5).
