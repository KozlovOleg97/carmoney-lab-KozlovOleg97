# Grill-лог MILEAGE: правило пробега в решении по заявке

- Дата: 2026-10-04
- Режим: Grill Me (1.5.1) — вопросы по одному, не больше шести, только влияющие на реализацию.
- Задача: добавить в расчёт решения по заявке проверку «пробег авто не больше
  400 000 км, иначе решение review».
- Источники, сверенные до вопросов: `docs/setup/code_map.md`,
  `docs/plan/plan_MILEAGE.md`, `backend/src/Domain/DecisionEngine.php`,
  `backend/src/Domain/AssessmentService.php`,
  `backend/src/Domain/ApplicationValidator.php`, `backend/config/rules.php`.

## Что НЕ спрашивал — уже видно из документов и кода

- Граница включительная: `mileage <= 400 000` — решение по текущей логике LTV,
  `400 001` — правило срабатывает (`code_map.md`, раздел «Новое правило»;
  формулировка задачи «не больше 400 000»).
- Пробег не указан (отсутствие поля / `null`) → `ValidationException` с ключом
  `mileage`, решение не считается — существующее поведение
  (`ApplicationValidator.php:43–46`).
- Порог лежит в `backend/config/rules.php` — конвенция проекта (AGENTS.md,
  шапка `rules.php`).

## Вопрос 1. Приоритет правил (review vs reject)

Вопрос: пробег 400 001–500 000 км (валидный диапазон) при одновременно плохом
LTV > 85% (зона reject) — какое решение должно победить? В `plan_MILEAGE.md`
заложен первый вариант, но это смягчение риск-решения, поэтому подтверждено
у заказчика.

Варианты:

- `review (Recommended)` — правило пробега проверяется до веток LTV:
  `mileage > 400 000` всегда даёт review, даже если LTV давал reject
  (как заложено в `plan_MILEAGE.md`);
- `reject` — строгие решения не смягчаем: правило пробега понижает до review
  только потенциальный approve; при LTV > 85% остаётся reject.

**Ответ: `reject`.**

Рекомендация агента (review, по плану) отклонена заказчиком. Это отклонение
от `plan_MILEAGE.md`: там правило пробега проверялось первым и перекрывало
reject (`decide(95.0, 400001) → REVIEW`). Теперь reject-ветка LTV
приоритетнее правила пробега, план требует корректировки.

## Вопрос 2. Пустой пробег

Вопрос: пробег «не указан» — отсутствие поля и `null` уже дают
`ValidationException` (`ApplicationValidator.php:43–46`), решение не
считается. На границе два случая: пустая строка `''` приводится к `0` и
проходит как 0 км, а явный `0` км сейчас валиден (диапазон 0..500 000). Что
делаем в этой задаче?

Варианты:

- `Не трогать валидацию (Recommended)` — `'' → 0 км` и явный `0` остаются
  валидными, решение по LTV; правим только DecisionEngine + `rules.php`;
  дыру `''` фиксируем как известную и вне scope (как в `plan_MILEAGE.md`);
- `Отклонять ''` — ужесточить `ApplicationValidator`: пустая строка →
  `ValidationException` с ключом `mileage`; `0` км остаётся валидным.
  Расширяет scope задачи;
- `Отклонять '' и 0` — `''` и `0` км → `ValidationException`: ноль считаем
  «пробег не указан». Максимально расширяет scope.

**Ответ: `Не трогать валидацию`.** `'' → 0 км` и явный `0` остаются
валидными, решение по LTV; дыра `'' → 0` известна и вне scope;
`ApplicationValidator` не меняется.

## Вопрос 3. Лимит при review

Вопрос: review из-за пробега (LTV в зоне approve, но `mileage > 400 000`) —
какой `approved_limit` возвращать? Сейчас все не-approve решения получают 0
(`AssessmentService.php:39`).

Варианты:

- `0, как у всех review (Recommended)` — существующее правило «не approve → 0»
  не трогаем, отдельных изменений логики лимита не нужно;
- `Запрошенная сумма` — для review из-за пробега показывать
  `requested_amount` как ориентир для ручного рассмотрения — потребует
  отдельной логики лимита в `AssessmentService`.

**Ответ: `0, как у всех review`.** Логика лимита не меняется.

## Вопрос 4. Старые заявки

Вопрос: решение фиксируется в таблице `decisions` при создании заявки,
GET-эндпоинты читают сохранённое. Правило пробега действует только на новые
заявки или нужно пересчитать уже сохранённые решения?

Варианты:

- `Только новые заявки (Recommended)` — старые записи в `decisions` не
  трогаем и не пересчитываем, без миграций и скриптов; как заложено в
  `plan_MILEAGE.md`;
- `Пересчитать старые` — добавить миграцию/скрипт пересчёта сохранённых
  решений по новому правилу — заметное расширение scope, лучше отдельной
  задачей.

**Ответ: `Только новые заявки`.** Миграций и скриптов пересчёта нет.

## Вопрос 5. Границы задачи

Вопрос: меняем только домен и его сборку — `DecisionEngine` (правило +
сигнатура `decide(ltv, mileage)`), `AssessmentService` (передача пробега),
`AppFactory` (проводка порога), `rules.php` (новый ключ
`vehicle.review_mileage_km = 400000`), тесты. Вне scope: диапазон валидации
0..500 000, `ApplicationValidator`, репозиторий/схема/сид, HTTP-контроллер,
пересчёт старых заявок, LOAN-12, фронтенд и `mocks/`. Верно?

Варианты:

- `Да, радиус верный (Recommended)` — только домен + конфиг + тесты; всё
  остальное не трогаем;
- `Нужно расширить` — в радиус задачи надо захватить что-то ещё.

**Ответ: `Да, радиус верный`.**

## Итог интервью — решения для intent_MILEAGE.md

Источник каждого решения — ответ в этом интервью.

1. `mileage <= 400 000` — без эффекта; `mileage > 400 000` — понижение
   только approve до review. Reject не смягчается: при LTV > 85% решение
   остаётся reject независимо от пробега (порядок проверок в `decide()`:
   reject-ветка LTV → правило пробега → approve/review по LTV).
2. Валидация пробега не меняется: отсутствие/`null` → `ValidationException`
   (существующее поведение), `'' → 0 км` и явный `0` км валидны; дыра
   `'' → 0` — известная и вне scope.
3. `approved_limit` при review из-за пробега — `0`, как у всех не-approve
   решений.
4. Правило действует только на новые заявки; сохранённые `decisions` не
   пересчитываются.
5. Радиус: `DecisionEngine`, `AssessmentService` (передача `$input['mileage']`),
   `AppFactory`, `rules.php` (новый ключ `vehicle.review_mileage_km = 400000`),
   тесты. Вне scope: диапазон валидации 0..500 000, `ApplicationValidator`,
   репозиторий/схема/сид, HTTP-контроллер, пересчёт старых заявок, LOAN-12,
   фронтенд, `mocks/`.

Открытые вопросы интервью: нет — все пять закрыты ответами заказчика.
Следствие для плана: `plan_MILEAGE.md` требует корректировки под п. 1
(отказ от схемы «пробег проверяется первым», порядок
`decide(95.0, 400001)` меняется с REVIEW на REJECT).
